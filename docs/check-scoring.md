# How to Check Agent Scoring

This guide explains the current scoring workflow in this repository and how to verify that the scoring pipeline is working end to end.

## Goal

Confirm that:

- agent action events are logged in `audit/agent-actions`
- score evidence files are generated in `audit/agent-quality`
- score evidence passes validation
- summary reports are generated in `reports`
- the execution report reflects the current agent runs

## Prerequisites

- Node.js installed
- Run commands from the repository root for this project

Example:

```bash
cd E:\Agentic_Demo_V3
```

## Current workflow

The repository uses a two-step flow:

1. An agent writes a completion or failure event through `.github/scripts/log-agent-action.js`
2. The logger triggers a scoring refresh automatically unless `--skip-refresh` is passed

This is the default behavior in the current implementation.

### Automatic refresh after logging

When an event is logged, the script does this automatically:

```bash
node .github/scripts/log-agent-action.js --skill jira-story-readiness --status success --summary "Ready for review" --jira-story-key KAN-7
```

If you want to skip the refresh for a specific run:

```bash
node .github/scripts/log-agent-action.js --skill jira-story-readiness --status success --summary "Manual review" --jira-story-key KAN-9 --skip-refresh
```

## Manual verification path

Use this when you want to force the full refresh explicitly.

```bash
node .github/scripts/refresh-agent-scoring.js --standalone
```

### What the refresh command does

It runs, in order:

1. `.github/scripts/generate-agent-execution-report.js --standalone`
2. `.github/scripts/generate-agent-quality-evidence.js`
3. `.github/scripts/validate-agent-quality-evidence.js`
4. `.github/scripts/generate-agent-quality-report.js`

This is the current manual verification path and the same path used by the logger-triggered refresh.

## Expected outputs

### Agent action logs

Location:

- `audit/agent-actions/`

Each JSON file stores a single event such as:

- `agent_task_completed`
- `agent_task_failed`
- `agent_usage_reported`

### Score evidence files

Location:

- `audit/agent-quality/`

The generated files are named in the form:

```text
<timestamp>_<skill>_evt-<eventid>.score.json
```

Example:

```text
audit/agent-quality/2026-09-29T08-35-09-258Z_jira-story-readiness_evt-20260929-083509258.score.json
```

### Summary reports

Location:

- `reports/agent-quality-report.csv`
- `reports/agent-quality-trends.csv`
- `reports/agent-execution-report.csv`

## Current score-evidence schema

The current generated JSON includes the following important fields.

### Top level

- `score_event_version`
- `generated_at`
- `source_event`
- `metric_version`
- `outcome_score`
- `confidence_score`
- `confidence_band`
- `summary_line`
- `detail_summary`
- `recommendation`
- `primary_reason_code`
- `missing_metric_list`
- `metric_explanations`
- `outcome_weights`
- `metrics`
- `confidence_factors`

### Source event payload

Inside `source_event`, the current files include:

- `event_id`
- `correlation_id`
- `jira_story_key`
- `skill`
- `actor_name`
- `actor_id`
- `status`
- `event_timestamp`
- `workflow_stage`
- `message`
- `source_file`

### Metric structure

Each metric entry includes:

- `key`
- `label`
- `weight`
- `value`
- `raw_inputs`
- `reason_code` when the value is null

### Confidence structure

`confidence_factors` contains entries like:

- `evidence_completeness`
- `validation_pass_rate`
- `historical_accuracy`

and includes a `value` plus optional `reason_code`.

## Current report schema

### Agent execution report

Generated by `.github/scripts/generate-agent-execution-report.js`.

The CSV header is currently:

```csv
Timestamp,Skill,ActorName,ActorId,JiraStoryKey,CorrelationId,Status,WorkflowStage,Summary,EventId
```

This is the report you should inspect when verifying the actual logged agent runs.

- `CorrelationId`

- `PrimaryReasonCode`
- `MissingMetrics`

## Manual validation steps

### Step 1: Generate score evidence

```bash
node .github/scripts/generate-agent-quality-evidence.js
```

Expected result:

- new files appear under `audit/agent-quality`
- each file contains the schema described above

### Step 2: Validate schema

```bash
node .github/scripts/validate-agent-quality-evidence.js
```

Expected result:

- validation completes successfully
- exit code is `0`

### Step 3: Generate quality report

```bash
node .github/scripts/generate-agent-quality-report.js
```

Expected result:

- `reports/agent-quality-report.csv`
- `reports/agent-quality-trends.csv`

### Step 4: Regenerate execution report

```bash
node .github/scripts/generate-agent-execution-report.js --standalone
```

Expected result:

- `reports/agent-execution-report.csv` is refreshed

```bash
node --test .github/scripts/tests/agent-quality-scripts.test.js
```

Expected result:

- all tests pass
- exit code `0`

## Troubleshooting

### No score files generated

Check:

- `audit/agent-actions` has valid completion/failure event JSON files
- the event files are valid JSON
- the refresh script was allowed to run

### Validation fails

Check:

- missing required fields
- invalid metric keys or null handling
- invalid `reason_code` values

### Execution report is empty or stale

Run:

```bash
node .github/scripts/generate-agent-execution-report.js --standalone
```

Then regenerate evidence and reports if needed:

```bash
node .github/scripts/refresh-agent-scoring.js --standalone
```

## Recommended daily workflow

For normal usage, the recommended pattern is:

1. log the agent outcome with `.github/scripts/log-agent-action.js`
2. let the logger trigger the refresh automatically
3. confirm the files exist under `audit/agent-quality` and `reports`

This is the current default behavior and is the least error-prone workflow for consistent audit and score generation.

The repo is no longer aligned with the older “simple score guide” assumption. The current implementation includes richer score payloads, explicit summary text, and richer CSV outputs. This document reflects the current live behavior rather than the earlier simplified version.
